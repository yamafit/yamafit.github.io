## 1. まず読むところ（要約）

### 1.1 作るもの
商品情報とパーツ情報を入力すると、30秒の縦型動画（1080×1920、ナレーション・BGM付き）を書き出す管理画面です。Macのブラウザで操作し、書き出しはクラウド（GitHub Actions）で行います。Macだけで書き出す経路も残します。

### 1.2 採用する構成

| 役割 | 採用 | 一言でいう理由 |
|---|---|---|
| 管理画面 | Vite + React + TypeScript | 指示どおり。画面数が7つあり、入力チェックが多いため |
| 3D描画 | three.js（直接使う） | 「時刻tを渡すと1枚描く」関数にでき、プレビューと書き出しで同じ絵になる（→変更提案 16章） |
| フレーム取得 | Playwright（ヘッドレスChromium） | 指示どおり。事前計測で動作と再現性を確認済み |
| エンコード・音声合成 | ffmpeg | 指示どおり。H.264/AACと音量調整をこれ1つで行える |
| ナレーション | OpenAI の音声合成API | すでにこのリポジトリでOpenAIのキーを使っており、新しい契約が要らない |
| BGM | 再配布が許可された音源（CC0）に限定 | リポジトリが公開のため、再配布禁止の音源は置けない |
| クラウド | GitHub Actions | すでに毎日使っている仕組み。公開リポジトリなので追加費用なし |

### 1.3 承認をお願いしたいこと（6点）
詳しくは 18章にまとめています。

1. クラウドは GitHub Actions を使う（公開リポジトリのため、ジョブに入れたデータは誰でも見られる状態になる）
2. `.github/workflows/` に新しいファイルを1つだけ追加する（既存ファイルは変更しない）
3. ナレーションは OpenAI の音声合成を使う
4. 3D描画は three.js を直接使い、React Three Fiber は使わない
5. 分解シーンは「紹介するパーツ数で1パーツの時間が決まる」ルールにする（推奨3〜4個）
6. BGMは再配布可能なライセンス（CC0）の音源に限る

### 1.4 正直にお伝えしておく制約
- **MVPの3Dは仮モデルです。** 箱や円筒を組み合わせた形で、実物の形・ロゴ・素材感は再現しません。書き出した動画には「検証用・公開不可」の透かしが入ります。
- **商品画像1枚から正確な3Dモデルは作れません。** MVPでは画像から色だけを取り出します。公開できる品質の動画には、商品ごとの3Dモデル（glbファイル）が別途必要です。その入手方法は MVP の後で決める必要があります（17章）。
- **分解シーンは10秒です。** 7パーツすべてを音声で説明する時間はありません（9.3節）。

## 2. 事前に確認したこと

### 2.1 リポジトリの現状
- `yamafit/yamafit.github.io` は**公開リポジトリ**です。
- GitHub Actions のワークフローが17本あり、そのうち動画投稿用は `ubuntu-24.04` 固定で Playwright と ffmpeg を使っています。今回も同じ土台に揃えます。
- README によると `OPENAI_API_KEY` が GitHub の Secrets に登録済みです（実際の登録状況はこちらからは見えません）。
- ルートの `.gitignore` は `node_modules/`、`out/`、`.env` をすでに除外しています。
- サイトのロゴは文字（「ヤマフィット」＋「YAMAFIT」）で、**ロゴの画像ファイルはリポジトリにありません。**
- サイトの色と書体は `css/style.css` にあります（緑 `#1F5A43`、文字 `#14231C`、背景 `#F4F5F1`、アクセント `#C4391D`、Zen Kaku Gothic New、IBM Plex Mono）。
- `data/products.json` にザックが128件あり、特徴・スペック・情報源URLを持っています（将来の連携候補。MVPの範囲外）。

### 2.2 描画速度と再現性の事前計測
計画の見積もりを実測に基づかせるため、使い捨ての検証コードで計測しました（リポジトリには入れていません）。

- 計測環境：この開発用クラウド環境（4 vCPU、メモリ15GB、GPUなし）。GitHub Actions の公開リポジトリ向け標準ランナー（4 vCPU、16GB）とほぼ同じ規模です。
- 内容：9個の部品でできた仮のザック、影あり、1080×1920、文字の合成あり。

| 項目 | 結果 |
|---|---|
| GPUなしのヘッドレスChromiumでWebGL描画 | 動作する（ソフトウェア描画） |
| 1フレームあたりの時間（描画→PNG→ffmpegでH.264化まで） | 約0.40秒 |
| 30秒（900フレーム）の見込み | 約6分 |
| 同じ入力を別々に2回実行したときの画素 | 確認した7時点すべてで完全一致 |
| ファイルサイズ（5秒で1.4MB） | 30秒の映像で約8〜9MBの見込み |

フレームの受け渡し方法も比べました。無圧縮の画素をそのまま送る方法は1フレーム約1.3秒かかり、PNGにして送る方法（約0.40秒）の3倍以上遅かったため、**PNGで受け渡す方式**を採用します。PNGは可逆圧縮なので画質は落ちません。

未計測のもの：MacBook Air 上での書き出し時間（Phase 1 で計測手順を用意します）。

## 3. 技術選定と採用理由

### 3.1 3D描画：three.js
- ブラウザで動き、Macでもクラウドでも同じコードが使えます。
- 素材の質感（粗さ・金属感）、影、スタジオ風の照明を標準機能で表現できます。
- glb（glTF 2.0）の読み込みが標準で付いており、商品別モデルへの差し替えに対応できます。
- 照明用の環境マップは three.js 同梱の `RoomEnvironment`（プログラムで生成、MITライセンス）を使います。外部のHDR画像を使わないので、ライセンス確認もネットワーク接続も不要です。

### 3.2 描画の取得：Playwright ＋ 決定論的な設計
- 書き出し専用のページ（管理画面なし）を開き、`renderAt(t)` を 0/30秒、1/30秒、…と900回呼びます。
- 描画は次の規則で「時刻tだけで決まる」ようにします。

| 規則 | 内容 |
|---|---|
| 状態を持ち越さない | 500フレーム目だけを描いても、0から順に描いても同じ絵になる |
| 時計と乱数を使わない | 描画の中で現在時刻・経過時間・`Math.random` を使わない |
| 素材を待つ | フォント・モデル・画像をすべて読み込んでから1フレーム目を描く |
| 条件を固定する | キャンバス1080×1920、画素比1、Chromiumのバージョンを固定 |
| 記録する | 各フレームのハッシュ値を `render-report.json` に残す |

- **再現性の範囲**：同じ環境なら画素が完全に一致します（計測済み）。MacのGPU描画とクラウドのソフトウェア描画では、見た目は同じでも画素単位では一致しません。そのため**クラウド書き出しを正本**とします。

### 3.3 テキスト：合成用キャンバスに描いて焼き込む
- 3Dを描いたあと、同じフレームに2Dキャンバスで文字・引き出し線・ロゴ・透かしを重ねます。
- HTMLの文字は使いません。プレビューも同じ合成処理を通すので、見たままが書き出されます。
- フォントはファイルを同梱します（Zen Kaku Gothic New と IBM Plex Mono。どちらも SIL Open Font License で同梱可能）。Google Fonts への接続には頼りません。

### 3.4 エンコード：ffmpeg
- 映像：PNGを受け取って H.264（yuv420p）にします。
- 音声：ナレーションとBGMを混ぜ、AACにして映像と合わせます。
- 検証：`ffprobe` で解像度・尺・コーデックを確認します。
- クラウドでは apt で入れます（既存ワークフローと同じ）。Macでは `npm install` のときに自動で入る `ffmpeg-static` を使い、Homebrew を不要にします。

### 3.5 ナレーション：OpenAI の音声合成API（`gpt-4o-mini-tts`）

| 候補 | 日本語 | 読み方の指定 | 必要な準備 | 料金の目安 |
|---|---|---|---|---|
| **OpenAI（採用）** | 対応 | 専用記法なし（読み上げ用テキストを別に持つことで対応） | **なし**（既存のキーを使う） | 音声1分あたり約0.015ドル |
| Google Cloud Text-to-Speech | 対応 | SSMLで指定可 | GCPプロジェクト、課金設定、サービスアカウント | 100万文字あたり16〜30ドル |
| Azure AI Speech | 対応 | SSMLで指定可 | Azure契約、Speechリソース作成 | 100万文字あたり約15〜22ドル |

- 採用理由：30秒の原稿は150〜170文字ほどで、どの候補でも1本あたり数円以下です。料金では差がつきません。差がつくのは準備の手間で、OpenAI だけが新しい契約と鍵の発行なしで始められます。
- 弱点と対策：漢字や型番を読み間違えることがあります。対策として、画面に出す文とは別に「読み上げ用テキスト」（例：雨蓋→あまぶた）を持てるようにし、書き出し前の試聴を必須にします。
- 乗り換えの余地：音声合成の呼び出しは1ファイルに閉じ込めます。読み間違いが許容できなければ、そのファイルの差し替えで Azure や Google に切り替えられます。
- 注意：OpenAI の利用規定は、AI音声であることを視聴者に明示するよう求めています。動画の最後に小さく「音声：AI合成」と表示します（サイトの「AIで作成したイメージ」表記と同じ考え方です）。
- 料金は第三者サイトの掲載値です。Phase 3 の開始時に公式の料金ページで確認します。

### 3.6 BGM：CC0 の音源に限定
- リポジトリが公開なので、BGMファイルを置くと「音源そのものの再配布」になります。多くのフリーBGMサイト（DOVA-SYNDROME など）は動画での利用は認めていても、音源ファイルの再配布は禁止しています。
- そのため、**再配布が認められている CC0（権利放棄）の音源だけ**を使います。クレジット表記も不要です。
- `assets/audio/LICENSE.md` に、曲名・作者・入手元URL・ライセンス・入手日を記録します。
- AI生成音楽は MVP では使いません。使う場合の確認項目は、(1) 生成サービスの有料プランで商用利用が認められているか、(2) 生成物をリポジトリに置いてよいか、(3) 各SNSの規約に抵触しないか、の3点です。

### 3.7 クラウド：GitHub Actions
5章にまとめます。

### 3.8 採用しなかったもの

| 候補 | 採用しない理由 |
|---|---|
| Blender | MVPは仮モデルなので不要。商品別モデルを作る段階で改めて検討 |
| Python | Node.js だけで足りる。言語を増やさない |
| Remotion（React製の動画制作ライブラリ） | 似たことができるが、独自ライセンスで依存も大きい。指示の構成（Playwright＋ffmpeg）で足りると計測で確認できた |
| GPU付きのクラウド | GPUなしで900フレーム約6分。待てる時間なので不要 |
| ブラウザ内でのMP4直接エンコード | ブラウザの種類で対応が変わる。ffmpeg のほうが設定を固定でき、検証もしやすい |

## 4. 全体構成

### 4.1 処理の流れ

```
【Mac】
 ブラウザ（管理画面）──── ローカルサーバー（Node.js、このMacの中だけで動く）
   入力・編集・プレビュー      ├ プロジェクトの保存と読み込み
                               ├ ナレーション音声の生成（→ OpenAI）
                               ├ Macでの書き出し（Playwright → ffmpeg）
                               └ クラウドへのジョブ投入と受け取り（→ GitHub）

【クラウド：GitHub Actions】
 ジョブを受け取る → ヘッドレスChromiumで900フレーム描画 → ffmpegでMP4化
 → 検証（ffprobe）→ 結果用ブランチにMP4を置く → Macが受け取る
```

- プレビューと書き出しは同じ描画コード（`renderAt(t)`）を使います。
- ナレーション音声は一度作ったら保存し、プレビューにも書き出しにも同じファイルを使います。クラウド側では音声合成を呼び直しません（同じ音になり、料金も二重にかかりません）。
- APIキーはローカルサーバーだけが読みます。ブラウザの画面には渡しません。
- ローカルサーバーは `127.0.0.1` 限定で、外部からは接続できません。

### 4.2 フォルダ構成

```
tools/yamafit-video/
  README.md             使い方（Macでの準備と操作手順）
  package.json ほか設定ファイル
  docs/
    PLAN.md             この計画書
    CHECKLIST.md        シーンごとの確認表（Phase 2で作成）
  assets/
    logo/               ロゴ（提供されるまでは仮のロゴ）
    fonts/              同梱フォントとライセンス文
    audio/              BGMと LICENSE.md
  examples/sample-pack/ 動作確認用のサンプル（架空の商品であることを明記）
  src/
    core/               画面にもサーバーにも依存しない計算部分
                        （データの型と検証、タイムライン、原稿の組み立て、音声の配置）
    stage/              three.js の描画（仮モデル、glb読み込み、文字の合成）
    app/                管理画面（React）
    render.html         書き出し専用ページ
  server/               ローカルサーバー、書き出し、音声合成、クラウド連携
  tests/                ユニットテストとE2Eテスト
  projects/             プロジェクトの保存先（project.json はGitに入れる。写真・音声・3DモデルはGitに入れない）
  out/                  書き出したMP4（Gitには入れない）

.github/workflows/yamafit-video-render.yml   ← tools の外に追加する唯一のファイル
```

### 4.3 必要なライブラリ

| 種類 | ライブラリ | 用途 |
|---|---|---|
| 実行時 | react、react-dom | 管理画面 |
| 実行時 | three | 3D描画、glb読み込み |
| 実行時 | zod | 入力チェック（画面・保存ファイル・クラウドのジョブを1つの定義で検証） |
| 開発時 | vite、@vitejs/plugin-react、typescript | ビルドと型チェック |
| 開発時 | playwright、@playwright/test | フレーム取得、E2Eテスト |
| 開発時 | vitest | ユニットテスト |
| 任意 | ffmpeg-static | Mac用のffmpeg（システムにあればそちらを使う） |

- 状態管理ライブラリ、UI部品ライブラリ、Express などのサーバーフレームワークは使いません（React と Node.js の標準機能で足ります）。
- Node.js は 22 系（既存ワークフローと同じ）を前提にします。

## 5. クラウド

### 5.1 提供先と料金

| 項目 | 内容 |
|---|---|
| 提供先 | GitHub Actions（標準ランナー `ubuntu-24.04`、既存ワークフローと同じ固定） |
| GPU | 不要（2.2節の計測より） |
| 料金 | 公開リポジトリの標準ランナーは無料 |
| 1回の所要時間（目標） | ジョブ投入からMP4受け取りまで**15分以内**（準備2〜3分、描画6〜9分、音声合成と検証1分） |
| 打ち切り | 40分で自動停止 |
| ナレーション | 1本あたり約0.0075ドル（約1円）。作り直しを10回しても十数円 |
| BGM | 0円（CC0） |

商品別の3Dモデルに差し替えると、模様や部品が増えて描画時間が延びます。その時点で再計測します。

### 5.2 ジョブの受け渡し方法
Macにすでにある「git push できる状態」だけを使い、新しい鍵やツールを増やしません。

1. 管理画面の「クラウドで書き出す」を押す。
2. ローカルサーバーが、プロジェクトのデータを `video-jobs/<ジョブID>` というブランチに push する。作業中のファイルやブランチには触れません。
3. push をきっかけに GitHub Actions が起動し、描画・エンコード・検証を行う。
4. 完成したMP4と検証結果を `video-out/<ジョブID>` ブランチに置き、ジョブ用ブランチを消す。
5. ローカルサーバーが定期的に確認し、MP4を `out/` に保存して、結果用ブランチを消す。

- 画面の進捗表示は「待機中／実行中／完了／失敗」の4段階です。
- キャンセルは、ジョブ用ブランチを消すことで行います（クラウド側が描画の途中で確認して止まります）。
- クラウドの書き出しは Secrets（APIキー）を一切使いません。

### 5.3 外部に送信するデータ

| 送信先 | 送るもの | 送らないもの | 公開範囲 |
|---|---|---|---|
| OpenAI（音声合成） | 読み上げ原稿（商品名、メーカー、特徴、パーツの役割）、声の指定 | 商品画像、3Dモデル、APIキー以外の個人情報 | OpenAIのAPI利用規約に従う |
| GitHub（ジョブ用・結果用ブランチ） | プロジェクトのデータ（商品情報、パーツ、演出の設定、画像から取り出した色）、ナレーション音声、BGM、ロゴ、完成したMP4 | **商品画像**（色の取り出しはMac内で行うため送らない）、APIキー | **誰でも見られる**（公開リポジトリのため） |
| npm など | なし（ライブラリのダウンロードのみ） | — | — |

- 商品別の3Dモデル（glb）を使う段階では、そのファイルもジョブに含まれ、公開状態になります。購入・外注したモデルは再配布が禁止されていることが多いため、その段階で非公開の受け渡し方法（非公開リポジトリなど）を検討します。
- 公開したくないデータがある場合は、Macでの書き出しを使えば外部に出ません。

## 6. データ設計

### 6.1 プロジェクトファイル（`project.json`）
1商品＝1フォルダ（`projects/<ID>/`）で、その中に `project.json`、画像、音声を置きます。

```jsonc
{
  "schemaVersion": 1,
  "id": "sample-pack-30",
  "category": "pack",                      // MVPは pack のみ。boots / wear は後日
  "product": {
    "name": "（商品名）",
    "maker": "（メーカー）",
    "modelNumber": "（型番）",
    "features": [                          // 1〜3件
      { "text": "（特徴。入力した文をそのまま使う）", "focusPartId": "back_panel" }
    ],
    "specs": [ { "label": "容量", "value": "30L" } ],
    "summary": "（まとめの一文）",
    "sources": [ { "url": "https://…", "checkedAt": "2026-11-13" } ]
  },
  "images": [ { "file": "images/front.jpg", "view": "front" } ],
  "model": {
    "kind": "placeholder-pack",            // 商品別モデルのときは "glb"
    "file": null,                          // "glb" のとき models/xxx.glb
    "heightCm": 60,
    "colors": { "main": "#2F6B4F", "sub": "#24523D", "strap": "#1C1C1C" }
  },
  "parts": [
    {
      "id": "top_lid",
      "label": "雨蓋",
      "role": "（役割。入力した文をそのまま使う）",
      "confirmed": true,                   // 実物にあると確認した印。false のパーツは描かない
      "highlight": true,                   // 分解シーンで紹介するか
      "order": 1,
      "nodes": ["top_lid"],                // glb内の部品名
      "explode": { "dir": [0, 1, 0], "distanceCm": 35 }
    }
  ],
  "narration": { "voice": "…", "speed": 1.0, "segments": [ /* 9章 */ ] },
  "bgm": { "file": "…", "volumeDb": -18, "duckDb": -10 },
  "direction": { /* 12章の演出パラメータ */ },
  "output": { "watermark": true }
}
```

### 6.2 「実際に存在する部品だけ」を守る仕組み
- 描かれるのは、`parts` に登録され、かつ `confirmed: true` のパーツだけです。
- 仮モデルも同じ規則に従います。チェストストラップが未登録なら、仮モデルからその部品を消します（説明を省くだけでなく、形としても出しません）。
- 役割の説明文は入力欄の文をそのまま使います。システムが文を作ることはありません。
- 入力欄には「公式ページで確認しましたか」の確認欄を付けます。

### 6.3 ザックのパーツID

| ID | 表示名 |
|---|---|
| `main_compartment` | メイン収納部（必須。本体として常に表示） |
| `top_lid` | 雨蓋 |
| `shoulder_harness` | ショルダーハーネス |
| `back_panel` | 背面パネル |
| `hip_belt` | ヒップベルト |
| `side_pocket` | サイドポケット |
| `chest_strap` | チェストストラップ |

カテゴリーごとの候補パーツは1ファイルで定義します。登山靴（アッパー、シューレース、シュータン、ミッドソール、アウトソール、トゥガード、ヒールカウンター）は、同じ形のファイルを足すことで追加できる構造にします。MVPでは実装しません。

### 6.4 商品別モデル（glb）の規格

| 項目 | 規定 |
|---|---|
| 形式 | glTF 2.0 のバイナリ（`.glb`）。画像は埋め込み。30MB以下 |
| 単位 | ファイルの中は glTF の標準どおりメートル。`project.json` の寸法と分解距離は cm（→16章） |
| 向き | 上が +Y。正面（背負う人の背中と反対側）が +Z |
| 原点 | 底面の中央（床が y=0） |
| 部品名 | ノード名をパーツIDにする。左右があるものは `side_pocket.L` と `side_pocket.R` のように後ろに付ける |
| 対応表 | `parts[].nodes` が正。ノード名はその初期値として使う |
| 対応のない部品 | 本体の一部として扱い（分解しない）、「3Dモデル確認」画面に警告を出す |
| 寸法の確認 | 読み込み時にモデルの高さと `heightCm` を比べ、20%以上違えば警告（単位の間違いを見つけるため） |
| 圧縮 | MVPでは Draco などの圧縮は使わない |

MVPの最後に、仮モデルを glb に書き出したものを読み込ませ、差し替えの経路が実際に動くことを確認します。

## 7. 仮モデルと入力画像の扱い

### 7.1 仮モデル
- 角を丸めた箱、円筒、輪などの基本形状を組み合わせて、7つのパーツを持つザックの形を作ります。
- 実物の形・ロゴ・縫い目・素材感は再現しません。
- 透かし「検証用・公開不可（仮3Dモデル）」を全フレームに入れます。既定はONです。仮モデルのまま透かしをOFFにしようとすると、確認の警告を出します。
- 管理画面の「3Dモデル確認」と書き出し完了の画面に、「この3Dは仮モデルで、実物の形とは異なります」と明記します。

### 7.2 入力画像の使い方（比較と選択）

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| A. 表面に貼る | 商品写真を仮モデルの表面に投影する | 一見それらしく見える | 形が違うので絵が歪む。裏側は情報がない。**正確なモデルのように見えてしまい、誤認を招く** |
| **B. 色だけ使う（採用）** | 写真から主要な色を2〜3色取り出し、仮モデルに塗る | 実物の色に近づく。何を参考にしたかが明確 | 柄やロゴは再現されない |
| C. 参照表示のみ | 画面で写真を横に並べて見比べるだけ | 誤認の余地がない | 動画には何も反映されない |

**B を採用します。** A は最重要原則（誤認させない）に反するため採用しません。取り出した色は画面に表示し、色見本で手直しできるようにします。C の「写真を横に並べる」は「3Dモデル確認」画面の機能として併用します。色の取り出しはMacのブラウザ内で行い、画像は外部に送りません。

### 7.3 実物写真のカード（2026-11-13 追加）
商品写真をいただいたのを受けて、写真そのものを動画の中に「実物写真」と明記したカードとして表示する機能を追加しました。3Dモデルに貼るのではなく、加工しない写真を別枠で見せるので、再現精度の原則に反しません。

| 場面 | 表示する写真 |
|---|---|
| 全体像（0〜5秒） | 正面の写真（左下） |
| 特徴の紹介（5〜12秒） | そのパーツがある側の写真（背面のパーツなら背面の写真） |
| 分解（12〜22秒） | 表示しない（パーツの説明の場所を空ける） |
| 再組み立て後の1回転（〜27秒） | 正面と背面を左右に並べる |
| まとめ（27〜30秒） | 表示しない（まとめの文とロゴの場所を空ける） |

- 設定で表示しないようにもできます（`direction.showPhotos`）。
- カードの大きさと位置は仮のものです。文字を含めた最終的な配置は Phase 2 で決めます。
- **写真はリポジトリに入れません**（公開リポジトリのため）。`projects/<ID>/images/` に置き、Git の対象から外しています。
- **クラウド書き出しとの関係**：写真のカードを使う動画をクラウドで書き出すには、写真をジョブに含める必要があり、公開状態になります。Phase 5 で、(1) 写真つきの動画はMacで書き出す、(2) 利用条件を確認できた写真だけクラウドに送る、のどちらにするかを決めます。
- メーカーの公式画像を使う場合は、公開前に利用条件の確認が必要です（運営者の判断）。

### 7.4 写真の輪郭に合わせた近似モデル（2026-11-13 追加）
「3Dの形を写真のザックに近づけたい」というご要望を受けて、仮モデルと商品別モデル（glb）の中間にあたる方法を追加しました。

| モデルの種類 | 形の決め方 | 実物との近さ | 費用 |
|---|---|---|---|
| 仮モデル（`placeholder-pack`） | どの商品にも同じ形 | 低い | なし |
| **近似モデル（`profile-pack`）** | 商品写真の輪郭と公式の寸法から決めた数値 | 全体の形とパーツの配置は近い。細部は再現しない | なし |
| 商品別モデル（`glb`） | スキャンやモデリングで作ったファイル | 高い（作り方しだい） | 作り方しだい |

- 入力は数値のデータ（`model.shape`）です。本体の輪郭（高さごとの幅と奥行き）、ストラップやベルトの道筋、ポケットの範囲を、cm で書きます。
- パーツごとに分かれた形で作るので、分解の演出がそのまま使えます。
- ポケットと背面パネルは、本体の表面に沿わせて作ります（本体の形を変えれば一緒に変わります）。
- 写真から読み取れない所（横から見た奥行きなど）は推定になります。どこが測定で、どこが推定かは、商品ごとの README に記録します。
- 透かしの文言は「写真をもとにした近似モデルです（細部は実物と異なります）」に変わります。
- いまは数値を手作業で決めています。管理画面（Phase 4）で、写真の輪郭から数値の下書きを自動で作る機能を検討します。

## 8. 映像設計

### 8.1 タイムライン（30秒＝900フレーム）

| 時刻 | シーン | 3Dの動き | 画面の文字 |
|---|---|---|---|
| 0〜5秒 | 全体像 | 全体が映る距離で、ゆっくり回転 | メーカー名、商品名 |
| 5〜12秒 | 特徴の紹介 | 特徴に関係するパーツへ接近（特徴1件につき約3.5秒） | 特徴の文 |
| 12〜22秒 | 分解 | 1.2秒かけて分解。その後、紹介するパーツを1つずつ強調（他は薄くする） | パーツ名、役割、引き出し線 |
| 22〜27秒 | 再組み立て | 1.5秒で元に戻し、残り3.5秒で360度回転 | なし（商品名を小さく） |
| 27〜30秒 | まとめ | 全体が映る位置で静止に近づく | まとめの文、ロゴ、「音声：AI合成」 |

- シーンの境目でカメラやパーツが飛ばないよう、前後のシーンで位置を必ず一致させます（テストで確認）。
- 再組み立て後のパーツ位置は、分解前と完全に同じ値に戻します（テストで確認）。

### 8.2 文字の規則

| 種類 | 行数と文字数の上限 | あふれたとき |
|---|---|---|
| 商品名 | 2行まで | 文字を段階的に小さくする |
| 特徴 | 2行×14文字 | 入力時に警告 |
| パーツ名 | 1行 | 入力時に警告 |
| パーツの役割 | 2行×12文字 | 入力時に警告 |
| まとめ | 3行×14文字 | 入力時に警告 |

- 改行は日本語の禁則（行頭に「、」「。」を置かない など）に従います。
- 上限を超えた文を黙って切り捨てることはしません。入力の段階で直してもらいます。

### 8.3 文字を置かない領域（セーフエリア）
各SNSのボタンや説明文に隠れないよう、文字は次の内側に置きます。

| 位置 | 余白の初期値 |
|---|---|
| 上 | 240px |
| 下 | 400px |
| 左 | 60px |
| 右 | 140px |

これは目安の値です（各アプリの画面は変わるため）。プレビューにガイド線を表示でき、値は設定で変えられます。

### 8.4 照明と背景
- キーライト（斜め前上から、影を落とす）、フィルライト（反対側から弱く）、リムライト（後ろから輪郭を出す）の3灯。
- 環境マップは three.js 同梱の `RoomEnvironment`。
- 背景は撮影スタジオ風の単色グラデーション。床にはやわらかい影だけを落とします。
- 背景色はサイトの色に合わせた3種類（明るい・緑・暗い）から選べます。

## 9. 音声設計

### 9.1 ナレーション原稿の組み立て
原稿は入力された文をつなぐだけです。新しい事実は足しません。

| シーン | 原稿の作り方 |
|---|---|
| 全体像 | 「{メーカー}、{商品名}。」 |
| 特徴の紹介 | 特徴の文をそのまま |
| 分解 | 「{パーツ名}。{役割}」をパーツごとに |
| 再組み立て | 定型文（初期値「パーツを戻して、もう一度全体を見てみましょう。」） |
| まとめ | まとめの文＋定型文（初期値「詳しくはヤマフィットで。」） |

- 定型文は商品の事実を含まないつなぎの言葉で、画面で編集できます。
- 各区切りには「画面に出す文」と「読み上げ用テキスト」を持たせます。読み間違いは読み上げ用だけをひらがなに直して対処します。
- 「最軽量」「日本一」「完全防水」などの語が原稿にあると、根拠の確認を促す警告を出します。

### 9.2 尺の検査
- 入力中：文字数から読み上げ時間を見積もって表示します（1秒あたり約5.5文字で計算）。
- 音声の生成後：実際の音声の長さを測り、シーンの時間と比べます。こちらが正式な判定です。
- 超えた場合：「あと○文字短くしてください」と警告し、書き出しを止めます。映像の長さは変えません。

| シーン | 使える時間 | 文字数の目安 |
|---|---|---|
| 全体像（5秒） | 約4.4秒 | 約24文字 |
| 特徴の紹介（7秒） | 約6.4秒 | 約35文字 |
| 分解（10秒） | 9.3節 | 9.3節 |
| 再組み立て（5秒） | 約4.4秒 | 約24文字 |
| まとめ（3秒） | 約2.4秒 | 約13文字 |

### 9.3 分解シーンの時間配分（承認をお願いしたい点）
分解シーンは10秒で、分解の動きに1.2秒、余白に0.3秒使うため、説明に使えるのは約8.5秒です。これを紹介するパーツ数で均等に割ります。

| 紹介するパーツ数 | 1パーツの時間 | 読み上げられる文字数の目安 |
|---|---|---|
| 3 | 約2.8秒 | 約13文字（パーツ名を含む） |
| 4 | 約2.1秒 | 約10文字 |
| 5 | 約1.7秒 | 約7文字 |
| 7 | 約1.2秒 | 約5文字（パーツ名を読むだけ） |

提案するルール：
- 登録して確認済みのパーツは**すべて分解して表示**します。
- そのうち「紹介する」に印を付けたパーツだけを、1つずつ強調して説明します。
- **紹介するパーツは3〜4個を推奨**し、5個以上にすると「説明が短くなります」と警告します。
- 役割の文が読み上げ時間に収まらないときは、読み上げ用テキストを短くするか、紹介するパーツを減らしていただきます。システムが文を縮めることはしません。
- 画面の文字も同じ時間しか出ないため、役割の文は入力の上限（24文字）より短いほうが読みやすくなります。表示時間に対して文字が多いときは警告を出します。警告の基準（1秒あたり4〜6文字が目安）は、Phase 2 で実際の映像を見て決めます。
- 役割の説明を全部読ませたい場合は、動画を30秒より長くする必要があります（今回の仕様の範囲外）。

### 9.4 BGMとミックス
- BGMは30秒に合わせて切り、頭0.5秒でフェードイン、最後1.0秒でフェードアウトします。
- ナレーションが流れている間はBGMを自動で下げます（ダッキング）。ナレーションの開始・終了時刻は分かっているので、音量の上げ下げを時刻で決めます。プレビューと書き出しで同じ数値を使うため、聞こえ方が一致します。
- 仕上がりの音量はSNS向けの一般的な水準（−14 LUFS前後）に揃え、音割れを防ぐ上限をかけます。

## 10. 管理画面

### 10.1 画面の形
上から順に進む7ステップ形式です。画面の右側に常に9:16のプレビューを表示します。入力内容は自動で保存します。

| ステップ | 内容 |
|---|---|
| 1. 商品画像 | 画像を選ぶ（1〜5枚）。正面・側面・背面・細部の区別を付ける |
| 2. 商品情報 | 商品名、メーカー、型番、特徴、スペック、まとめ、情報源URL、パーツ |

| 6. プレビュー | 再生、一時停止、シーク、音声付き。セーフエリアのガイド表示 |
| 7. 書き出し | 「クラウドで書き出す」「このMacで書き出す」。進捗、キャンセル、失敗時の再実行、検証結果の表示 |

### 10.2 商品情報の入力項目

| 項目 | 必須 | チェック |
|---|---|---|
| 商品名 | 必須 | 1〜40文字 |
| メーカー | 必須 | 1〜30文字 |
| 型番 | 必須 | 1〜40文字。ファイル名に使うため、使えない記号は `-` に置き換える |

| パーツ | 2個以上 | 候補から選ぶ。役割は24文字まで。「実物にあると確認した」の印が必要 |
| 画像 | 1枚以上 | JPEG・PNG・WebP。短い辺が1000px未満で警告、500px未満でエラー。1枚20MBまで |

### 10.3 エラーの表示文

| 場面 | 表示する文 |
|---|---|
| 画像が小さい | 画像が小さすぎます（短い辺 ○○px）。短い辺が1000px以上の画像を使ってください。 |

| 音声合成の失敗 | ナレーション音声を作れませんでした（理由：○○）。少し待ってから「もう一度作る」を押してください。 |
| BGM未設定 | BGMが選ばれていません。「演出とナレーション」でBGMを選んでください。 |
| APIキー未設定 | ナレーション用のAPIキーが設定されていません。`tools/yamafit-video/.env` に `OPENAI_API_KEY` を書いて、アプリを起動し直してください。（キーはこの画面には入力しません） |
| クラウド接続の失敗 | クラウドに接続できませんでした。インターネット接続を確認してください。「このMacで書き出す」に切り替えることもできます。 |
| ナレーションが長い | 「○○」のナレーションが○秒長すぎます。あと○文字ほど短くしてください。 |
| 書き出しの失敗 | 書き出しに失敗しました（○フレーム目）。「もう一度書き出す」を押してください。 |

### 10.4 保存と書き出しファイル名
- プロジェクトは `projects/<ID>/project.json` に保存し、一覧から読み込めます。
- 書き出しファイル名は `yamafit_{型番}_{YYYYMMDD}.mp4`、保存先は `out/` です。同じ名前がすでにあれば `_2`、`_3` を付けます。
- 画面の表示、コードのコメント、ドキュメントはすべて日本語で書きます。

## 12. 演出パラメータ（初期値と範囲）

| 分類 | 項目 | 初期値 | 範囲 |
|---|---|---|---|
| カメラ | 全体を映す距離（商品の高さの何倍か） | 3.1 | 1.8〜4.0 |
| カメラ | 接近したときの距離（パーツ全体が収まる距離より近くには寄らない） | 1.3 | 0.7〜2.0 |
| カメラ | 画角 | 30° | 20〜45° |
| カメラ | カメラの高さ（商品の高さに対する比） | 0.55 | 0.2〜1.0 |
| カメラ | 動きの緩急 | ゆっくり始まりゆっくり止まる（強） | 一定／弱／強／止まり際だけ |
| 回転 | 冒頭の回転速度 | 毎秒36° | 0〜90° |
| 回転 | 再組み立て後の1回転にかける時間 | 3.5秒 | 2.0〜3.5秒 |

範囲の組み合わせによってシーンの時間に収まらなくなる場合は、画面に警告を出します。

追加した項目：実物写真のカードを表示するか（初期値：表示する。7.3節）。

Phase 1 で実際の映像を見て変えた点：
- 「全体を映す距離」の初期値を 2.6 から 3.1 にしました。縦長の画面は横が狭く、2.6 では回転中にショルダーハーネスが画面からはみ出したためです。
- 「全体を映す距離」は、どの向きでも商品全体が収まる距離より近くにはなりません。雨蓋のない背の低い商品では、設定値のままだと回転中にはみ出すため、自動で必要な距離まで引きます。
- 接近するとき、パーツ全体が画面に収まる距離より近くには寄らないようにしました。近すぎると何のパーツか分からなくなるためです。

| 1 | 1080×1920、30fps、900フレーム、H.264、yuv420p | `ffprobe` の結果を自動で判定 |
| 2 | 音声がAACで入っている | 同上 |
| 3 | 尺が30.0秒±0.1秒 | 同上 |
| 4 | faststart になっている | ファイルの構造を自動で確認 |
| 5 | 同じ入力から同じフレームが出る | 同じ環境で2回書き出し、全フレームのハッシュ値を比較 |

テストの種類：
- ユニットテスト（vitest）：タイムライン、境目の連続性、分解と再組み立ての一致、入力チェック、原稿の組み立て、尺の見積もり、BGMの音量変化、ファイル名。
- 書き出しのE2Eテスト（Playwright）：サンプルからMP4を書き出し、上の1〜6を判定。短縮版（90フレーム）と完全版（900フレーム）を用意します。
- 管理画面のE2Eテスト（Playwright）：7ステップを最後まで進める流れと、エラーの表示。

## 15. Macでの使い方（予定）

## 16. 指示からの変更提案

| # | 指示の内容 | 提案 | 理由 |
|---|---|---|---|
| 1 | three.js（React Three Fiber） | three.js を直接使い、React Three Fiber は使わない | 描画を「時刻tを渡すと1枚描く」1つの関数にでき、プレビュー・書き出し・テストで同じものを使える。間に入る層が減り、再現性の確認がしやすい。ライブラリも1つ減る。管理画面は指示どおり React で作る |
| 2 | glbの単位はcm | glbファイルの中はメートル、`project.json` の寸法と分解距離はcm | glTF の規格が単位をメートルと定めている。規格どおりにしておけば、Blender などからそのまま書き出したファイルが使える |
| 3 | 既存サイトのファイルは変更しない | `.github/workflows/` に新規ファイルを1つ追加する | GitHub Actions のワークフローはこの場所にしか置けない。既存のファイルは変更しない |
| 4 | 透かしは設定で切り替え可能 | 仮モデルのまま透かしをOFFにするときは確認の警告を出す | 仮モデルの動画を誤って公開しないため |

1 について、指示どおり React Three Fiber を使うことも可能です。その場合は再現性を保つための作り込みが少し増えます。

## 17. リスクと制約

| リスク | 影響 | 対策 |
|---|---|---|
| **商品別3Dモデルの入手** | これがないと公開できる動画にならない。MVPの外で最も大きな課題 | MVPでは差し替えの経路だけ確認する。入手方法は下の選択肢から決める |
| 音声合成の読み間違い | 商品名や型番を誤って読む | 読み上げ用テキスト、試聴の必須化、提供元の切り替え余地 |
| 公開リポジトリでのデータ公開 | ジョブに入れたデータが誰でも見られる | 商品画像は送らない。BGMはCC0限定。非公開にしたい場合はMacで書き出す |
| GitHub Actions の仕様変更 | 既存ワークフローでも実例あり（ubuntuの更新でPlaywrightが動かなくなった） | OSとバージョンを固定する。Macでの書き出しを残す |
| クラウドとMacで画素が一致しない | 厳密な比較ができない | クラウド書き出しを正本とする。同じ環境内での一致を保証する |
| BGMの権利申し立て | SNS側で自動検出されることがある | CC0の音源を使い、出所を `LICENSE.md` に記録する |
| 商品画像・ロゴの権利 | メーカーの画像や商標の扱い | 画像は色の参考にだけ使い、外部に送らない。公開前の権利確認は運営者の判断（既存の方針と同じ） |

商品別3Dモデルの入手方法（MVPの後で決めること）：

| 方法 | 再現精度 | 手間と費用 | 備考 |
|---|---|---|---|
| 実物をスマホでスキャン | 形と色は高い | 実物が必要。部品ごとに分ける作業が別途必要 | 手元に商品があるなら現実的 |
| モデリングの外注 | 高い（資料しだい） | 1点ごとに費用と日数 | 再配布の条件に注意 |
| 自分でBlenderで作る | 作り手しだい | 学習と作業の時間が大きい | — |
| 画像から3Dを生成するAI | **低い**（見えない面は推測で作られる） | 安く速い | 最重要原則に反するため、使うなら「AIによる推定形状」と明示が必要 |
| **写真の輪郭と公式寸法から作る近似モデル（採用・7.4節）** | 全体の形とパーツ配置は近い。細部は再現しない | 費用なし。商品ごとに数値を決める作業が必要 | 推定した箇所を記録する。ロゴや切り替え線は入らない |

なお、3Dモデルが用意できない商品向けに、実物の写真そのものを動かして見せる「写真ベースの演出」を後から足すことも考えられます。写真は実物なので再現精度の問題が起きません。今回の範囲には含めません。
